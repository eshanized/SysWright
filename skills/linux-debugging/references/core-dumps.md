# Core Dumps, DWARF Symbols, and Post-Mortem Analysis

Comprehensive reference for core dump collection, systemd-coredump, DWARF debug info, and symbol resolution.

---

## 1. Core Dump Architecture on Linux

When a process receives an unhandled terminating signal (such as `SIGSEGV`, `SIGABRT`, `SIGBUS`, `SIGFPE`, `SIGILL`), the Linux kernel generates an ELF core dump recording the process's virtual memory address space, register states, thread list, and memory mappings (`/proc/PID/maps`).

### Key Signals Generating Core Dumps:
- `SIGSEGV` (11): Invalid memory reference (NULL pointer, page violation).
- `SIGABRT` (6): Abort signal generated by `abort()`, `assert()`, or glibc heap corruption checks.
- `SIGBUS` (7): Bus error (unaligned memory access or mmap beyond EOF).
- `SIGFPE` (8): Erroneous arithmetic operation (division by zero).
- `SIGILL` (4): Illegal instruction (corrupted code pointer, unsupported instruction set).

## 2. Kernel and systemd Configuration

### Checking and Enabling Limits:
```bash
# Check current core file size limit in shell
ulimit -c

# Enable unlimited core dumps for current shell session
ulimit -c unlimited

# Persistent limit in /etc/security/limits.conf
# <user>          soft    core            unlimited
# <user>          hard    core            unlimited
```

### systemd-coredump Management:
On modern systemd distributions, `/proc/sys/kernel/core_pattern` points to `systemd-coredump`:
```text
|/usr/lib/systemd/systemd-coredump %P %u %g %s %t %c %h
```

```bash
# List recent core dumps
coredumpctl list

# Display detailed metadata for the latest crash
coredumpctl info

# Launch GDB directly into the latest core dump
coredumpctl debug

# Extract the raw ELF core file to disk
coredumpctl dump -o /tmp/crash.core <PID_or_COMM>
```

## 3. DWARF Debug Symbols and Build IDs

Debug symbols map machine instructions back to source file lines and variable data types.

### The ELF `.note.gnu.build-id`:
Every modern Linux binary contains a unique 160-bit SHA-1 hash known as the Build ID:
```bash
readelf -n /usr/bin/my_app | grep "Build ID"
# Build ID: 8a7c9d2f012b4e8590623aef5c01bc81d45903b1
```
GDB checks that the core dump's Build ID matches the binary and symbol files.

### debuginfod: Automated Symbol Distribution
Modern Linux distributions (Arch Linux, Fedora, Debian, Ubuntu) provide `debuginfod` servers that allow GDB, `perf`, and `coredumpctl` to download matching debug symbols and source files on demand:
```bash
# Enable debuginfod in environment
export DEBUGINFOD_URLS="https://debuginfod.archlinux.org"

# GDB will automatically fetch debuginfo on load
gdb -q -ex "set debuginfod enabled on" -ex "file /usr/bin/my_app" -ex "core /tmp/crash.core"
```

## 4. Incomplete Backtrace Caveats

> [!IMPORTANT]
> When inspecting backtraces, look for unresolved frames:
> `?? () from /usr/lib/libc.so.6`
> This indicates missing debug symbols or a clobbered stack pointer (`%rsp`).
> **Rule**: Never declare a root cause diagnosis when the crash frame is inside an unresolved symbol (`??`). Install debuginfo packages (`valgrind`, `glibc-debug`, etc.) or enable `debuginfod` to inspect the exact crashing source line.
